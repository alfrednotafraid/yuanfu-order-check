# 设计说明（面试向）

## 一句话
定制家居订单交付链的"数据核对"AI 助手：把 生产→发货→运输→配送 四个环节的串货/少件/漏件校核，从人工核对变成"大模型听懂话、确定性代码做判断"的自动校核。

## 架构
```
用户(文字) → Coze 智能体(意图理解/抽单号/结果转人话)
           → 4 个校核工作流(HTTP 请求节点)
           → FastAPI 服务(本地) → MySQL(7 表, 13613 行, 全字段)
```
原则：**LLM 不参与任何判定**。单号解析、状态聚合、箱码集合比对全部是 SQL/Python，
同样输入永远得到同样输出（准确率可测），LLM 只做"理解问题"和"转述结果"两端的活。

## 四场景与规则映射（校验逻辑.docx → 代码）
| 场景 | 规则原文要点 | 实现 |
|---|---|---|
| 生产齐套 | 子单齐套状态聚合：全1/有0/全null | `production_check`：按 齐套/空 分组判 全量完成/部分生产/未启动 |
| 发货完整+城配仓到货 | 子单发货单号绑定率；干仓配入库状态 | `shipment_check`：绑定率 + 入库聚合双结论 |
| 运输串少漏 | 运输单应装箱码 vs 实扫全量比对 | `transport_check`：集合差=漏/多；反查箱码归属运输单≠本单=串货；重复扫码检出 |
| 配送齐套+合规 | 派送单明细 vs 实扫；装载归属合法性 | `delivery_check`：同上 + "同车不同单"判分货错误 |

## 关键取舍
1. **弃用 Coze 内置数据库，自建 MySQL + HTTP 节点。** 内置库单表上限 20 字段，生产订单实际 51 字段，参赛时被迫删字段；自建库全字段忠实落地，且 SQL 能力完整。代价：本地服务需内网穿透才能被 Coze 调用。
2. **校核确定化。** 参赛版把校核规则原文放知识库由 LLM 检索判断，结论不稳定。重做版规则逐条翻译为代码，知识库只留"话术/解释"用途。
3. **单号解析层。** 样例数据里订单号跨表号段不一致（物流单 D3369… vs 生产单 MD…），直接查会"查无此单"。`resolve_ship_codes` 按 prod→logistics 逐级解析成发货单号集合再查子单。
4. **异常靠构造而非原始数据。** 1379 条生产订单全部是"齐套/已发货/已入库"正常态，异常分支用输入侧构造（删箱码=漏、混入他车码=串、同车错单=分货错），9 条断言覆盖。
5. **数据安全（设计规则）。** 校核服务对业务表只读；校核留痕应写独立的 check_record 表，不触碰业务数据。

## 演进方向：规则表（回应大赛"学习力"）
把规则外置为数据：`check_rule(环节, 校核字段, 条件, 结论, 话术)`，代码读表执行，
新规则=插一行、不改代码。当前四场景条件均为"字段聚合+阈值"，可参数化；
集合比对类（串/漏）保留代码实现。本次未实现，接口已按场景拆分，改造不波及调用方。

## 已知限制
本地 demo 无鉴权、无并发优化；MySQL 5.7 无窗口函数（本场景不需要）；
穿透后的地址为临时地址；生产化需加 API key、只读账号、审计日志。
